CURRENT CONCLUSION
Direct expansion control looks viable on THIS firmware without DMD APIs or root:
/dev/expand is 0666, and installed system_ext SELinux CIL explicitly grants
appdomain open/read/write/ioctl access to its gpio_ctrl_device label. The same
file grants appdomain access to user_tty_device, matching accessible WK1-3.
This materially strengthens the earlier analysis, which only knew the DMD LoRa
app was privileged. It is a policy-source finding, not an actual GPIO ioctl test.

A clean 'DMD powers it, then our app takes over WK2' operation is NOT provided by
the existing DMD LoRa API. Its live service retains a serial reader and its normal
shutdown/disconnect path powers the expansion position off. Also, without an
EByte-compatible module the DMD initialization mode handshake fails and the
service shuts down. A custom Meshtastic module will not speak that EByte command
protocol. Use direct control first, or a dedicated power-only broker if required.

WHAT THE RECOVERED /dev/expand WRAPPER CAN DO
Native GpioControl opens the node O_RDWR; no DMD IPC is involved in these calls.
Recovered ARM64 ioctl requests:
  0xC01C5301 nativeSetPower(position,bool)
  0xC01C5302 nativeWriteIo(position,io,bool)
  0xC01C5303 nativeReadIo(position,io)
  0xC01C5309 nativeGetPosition(moduleType)
  0xC01C530A nativeGetType(position)
  0xC01C530B nativeReset()
ELora module-type ID = 38 / 0x26; RFID ID = 82 / 0x52.
Known argument-buffer fields are 32-bit:
  byte 0: I/O index for read/write-I/O requests
  byte 4: module type for getPosition / returned type for getType
  byte 8: state for setPower / writeIo / returned state for readIo
  byte 12: position
GetPosition reads the returned position at byte 12. GetType reads type at byte 4.
The request encoding specifies 28 bytes, but no original driver header was found;
full layout, valid I/O range and all remaining fields are unverified. nativeReset
supplies no explicit third ioctl argument. Do not invent a reset payload or call
unidentified request numbers. nativeReadIo returns Java true when its state field
is ZERO; this is inverted relative to a naive nonzero-to-bool interpretation.
Even discovery-looking _IOWR requests are driver operations, not proven inert.

DMD POWER SEQUENCE AND ITS LIMITS
ExpandManager.powerOn for position 2 calls:
  setPower(2,true)
  writeIo(2,1,true)
  delay 100 ms
It then opens WK2 O_RDWR and configures 9600/8N1. The physical function of logical
I/O 1 is not proven; 'enable' is an interpretation of its use in powerOn, not a
measured pin assignment. The model mdt781 uses other GPIOs for radio M0/M1;
mdt865 uses UART mode commands instead, so do not copy its M0/M1 mapping blindly.
The normal LoRa app enters EByte configuration mode and waits for a response.
Without a compatible radio, failure triggers shutdown, not a persistent power lease.

CAN DMD ENABLE POWER AND RELEASE ONLY THE UART?
Not through any operation in the recovered/documented Open API. The official
interface has isOpenMode, setOpenMode, readSettingsJson, writeSetting, sendMessage,
registerListener and unregisterListener. No power-only/close-UART/FD-lease method.
writeSetting("power",...) maps to AT+POWER (RF transmit power), not the expansion
supply setPower ioctl. It cannot be used as a connector-power enable command.
Open Mode means app-level radio messaging through DMD; SerialConnection keeps its
read coroutine alive. The data API sends strings and receives trimmed UTF-8,
which is not a binary-transparent Meshtastic transport.
On normal stop:
  LoraService.onDestroy -> EByteRepository.disconnect -> SerialConnection.close
  and ExpandManager.release -> powerOff(currentPosition), serial close.
The release helper itself powers off before closing its active SerialPort reference.
Recovery paths also disconnect/power-cycle/reinitialize and send EByte commands.
A second UART open may be allowed because the examined JNI code does not set
TIOCEXCL, but that is not ownership: reads can consume each other's data, writes
can interleave, termios state is shared, and DMD can remove power. Do not use this
as a handoff design. Do not use force-kill-and-hope-power-stays-on as a solution;
close/driver behavior and automatic restarts were not established.

PREFERRED DESIGN
First validate direct /dev/expand and WK2 access in the ordinary application.
If successful, keep DMD LoRa disabled, own the required expansion power/GPIO
sequence and raw UART in one process, and exchange Meshtastic protobuf bytes with
a real Meshtastic MCU/node wired to the port. Avoid DMD Open Mode entirely for
this architecture. Power acquisition/release must be explicit and measured.

If direct access fails on the real app/firmware, the useful app-level request to
Thork is a minimal expansion-power lease/broker that does NOT initialize an EByte
radio, open WK2, run a UART reader, send AT commands, or power off mid-lease.
A 'release UART but retain power' API would also have to stop every reader,
health/recovery timer and queued command, and decouple close from powerOff.
A power-only path before LoRa initialization is preferable because no Thork radio
is present. That is an app/service change using the existing SDK, rather than a
request for Thork to redesign OEM hardware or alter the radio chip firmware.
If no helper is needed, Thork can still forward existing Topicon documents.
